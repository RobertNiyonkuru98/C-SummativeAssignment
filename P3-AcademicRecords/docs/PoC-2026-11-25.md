# P3 - Student Academic Records and Performance Analytics System

## What the program does

Keeps an unknown number of students, each with their own courses and marks, in
dynamically allocated memory, and saves everything to a file so the data is
still there the next time the program runs.

```
------------------------- MENU -------------------------
 1. Register a new student
 2. Display all students
 3. View a student's details
 4. Update student information
 5. Delete a student record
 6. Add a course to a student
 7. Update marks for a course
 8. Display a student's performance
 9. Search students (ID / name / programme)
10. Sort students (ID / name / average / programme)
11. Generate the academic report
12. Save records to file
13. Load records from file
14. Exit
--------------------------------------------------------
```

### 1. Structures and the relationships between them

```c
typedef struct {
  char code[CODE_LEN];            // CS101
  char name[COURSE_NAME_LEN];     // C Programming
  int marks;                      // 78
  int max_marks;                  // 100
} Course;

typedef struct {
  int id;
  char first[NAME_LEN];
  char last[NAME_LEN];
  char programme[PROG_LEN];
  int year;
  int course_count;               // how many of the slots below are in use
  Course courses[MAX_COURSES];    // up to 8 courses per student
} Student;

typedef struct {
  Student *items;                 // the heap array of students
  int count;
  int capacity;
} Record;
```

One student owns an array of course records, and the `Record` owns a heap array
of students - so a student and their courses are one block, and adding a student
only ever moves student blocks around.

### 2. Dynamic memory

- The array starts with `calloc(INITIAL_CAP, sizeof(Student))`, so the first four
  students fit without touching the allocator.
- `ensure_capacity()` doubles the array with `realloc` whenever a student is
  registered and the array is full, into a temporary pointer so a failure keeps
  the old data.
- `shrink_if_sparse()` halves the array once it is only a quarter full, never
  below the starting size, and gives the memory back.
- `free()` is called once in `main` before the program exits.

The `[mem]` lines printed by the program make this visible. From
`docs/evidence/memory_growth_proof.txt`, registering nine more students and then
deleting ten:

```
  [mem] records 0 -> 4 slots
  [mem] records 4 -> 8 slots
  [mem] records 8 -> 16 slots
  [mem] records 16 -> 8 slots (shrunk)
  [mem] records 8 -> 4 slots (shrunk)
```

### 3. Searching — written by hand

Search is a plain loop over the array; no library helper does any of the work.
Three keys are supported:

- **ID** - exact comparison against `student.id`.
- **First or last name** - `contains_insensitive()` lowercases both strings and
  uses `strstr`, so searching for `grace` finds `Grace`.
- **Programme** - the same substring test on the programme field.

Every hit is printed with the student's average, and a search that matches
nothing says so instead of printing an empty table.

### 4. Sorting — written by hand

`sort_students()` is a bubble sort written out in full, with a comparison
chosen by a mode number. No `qsort` is used anywhere in this program, as the
brief requires.

| Mode | Compares on |
|---|---|
| 1 | student ID, ascending |
| 2 | last name, then first name, both case-insensitive |
| 3 | overall average, highest first |
| 4 | programme of study, alphabetical |

Captured result of sorting by average:

```

  1004   Grace        Iradukunda   Computer Science          2   69.0%
  1001   Aline        Uwase        Computer Science          2   65.7%
  1002   Kevin        Niyonzima    Information Technology    1   53.5%
```

### 5. Academic calculations

A student's average is weighted by the maximum marks of their courses:

```
student average = 100 * sum(marks) / sum(max_marks)
```

A course is passed when `marks >= 50% of max_marks`; a student is counted as
passing in the report when their overall average is at least 50%.

Both divisions are guarded: a student with no courses has an average of 0.0
instead of dividing by zero, and the report prints "not available" when no
student has any courses at all.

### 7. File handling and persistence

Records are saved as a plain text file, `academic_records.txt`, in blocks:

```
3
1003|Diane|Mukamana|Computer Science|3|3
CS102|Data Structures|88|100
CS201|Operating Systems|91|100
MA102|Linear Algebra|76|100
1004|Grace|Iradukunda|Computer Science|2|2
CS101|C Programming|80|100
CS103|Algorithms|58|100
...
```

The first line is the number of students; each student line holds the six
header fields, and the next `course_count` lines hold that student's courses.
Fields are separated by `|` so names with spaces are stored without quoting.

- Saving reports the number written: `Saved 4 student(s)`.
- Loading rebuilds the array with `ensure_capacity` as it reads, so the heap
  allocation is reconstructed rather than assumed.
- A missing file is not an error: the program says no saved file was found and
  starts empty.
- A file that is not in the expected format, that ends early, or that holds an
  invalid course count is reported with a specific message instead of loading
  junk into memory.

The run proves persistence: save four students, reload four, delete one, save
three - and the file on disk then starts with `3`.

### 8. Input validation

| Input | Rule | On violation |
|---|---|---|
| menu choice | 1 to 14 | message, menu shown again |
| student ID | whole number, positive, not already used | duplicate rejected naming the existing student |
| first / last name, programme | not empty, fits the field | rejected with the limit |
| year | 1 to 6 | rejected |
| course code | not already registered for that student | duplicate rejected |
| course limit | at most 8 courses per student | rejected |
| max marks | 1 to 1000 | rejected |
| marks | 0 to the course maximum | rejected |
| updating or deleting | the student must exist | "no student with ID" message |
| average with no courses | division by zero | average reported as 0.00 instead |

### 9. How it was tested

- Builds with `gcc -Wall -Wextra -std=c11 -pedantic` and **no warnings**
  (`docs/evidence/compile.log`).
- A full session exercising every operation is in `outputs/sample_run.txt`:
  register, view, add courses, update marks, performance, search, sort, report,
  save, load, delete, save again.
- Growth and shrink of the student array is captured separately in
  `docs/evidence/memory_growth_proof.txt`.
- The program was rebuilt with `-fsanitize=address,undefined` and run through
  the session with no errors and no leaks (`docs/evidence/sanitizer_run.txt`).
