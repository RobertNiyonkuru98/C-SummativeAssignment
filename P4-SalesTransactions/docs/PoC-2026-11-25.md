# P4 - Sales Transaction Processing and Analysis System

## What the program does

Records sales for a small business, runs several processing operations over them
**through function pointers**, filters them **through callbacks**, and keeps
everything in a file between runs.

```
------------------------- MENU -------------------------
 1. Add a new transaction
 2. Display all transactions
 3. Update a transaction
 4. Delete a transaction
 5. Process sales data (function pointers)
 6. Filter transactions (callbacks)
 7. Search transactions
 8. Sort transactions
 9. Generate the sales report
10. Save transactions to file
11. Load transactions from file
12. Exit
--------------------------------------------------------
```

### 1. Structures

```c
typedef struct {
  int id;                     // unique
  char product[PRODUCT_LEN];
  int quantity;
  double unit_price;
  double total;               // quantity * unit_price
  char date[DATE_LEN];        // YYYY-MM-DD
} Transaction;

typedef struct {
  Transaction *items;         // heap array
  int count;
  int capacity;
} Ledger;
```

The total amount is **derived, never typed**: `set_total()` recalculates it after
an add or an update, so the stored total can never drift from quantity x price.
The date is filled in automatically with the current day using `time()` and
`strftime()`.

### 2. Dynamic memory

- `calloc(INITIAL_CAP, sizeof(Transaction))` for the first four transactions.
- `ensure_capacity()` doubles the array with `realloc` when it fills up, into a
  temporary pointer so a failed allocation leaves the old data intact.
- `shrink_if_sparse()` halves the array once it is a quarter full.
- The program prints a `[mem]` line on every change, and `main()` frees the array
  once at the end.

### 3. Function pointers — three distinct uses

**a) Menu dispatch.** Every operation has the signature `void f(Ledger *)`, so
the menu calls through a table instead of a `switch`:

```c
typedef void (*LedgerOp)(Ledger *);
LedgerOp operations[] = {add_transaction, display_transactions, ..., quit_program};
operations[choice - 1](&ledger);
```

**b) Sales processing.** Menu option 5 offers five analysis operations, each of
which is a `SalesProc` function pointer taken from its own table:

```c
typedef void (*SalesProc)(const Ledger *);
SalesProc sales_operations[] = {proc_total_revenue, proc_average_value,
                                proc_highest, proc_lowest, proc_total_units};
sales_operations[choice - 1](ledger);
```

Captured output of the five operations:

```

  Average transaction     : 720800.00
  Highest transaction     : #1001 Laptop Pro 14 (1700000.00)
  Lowest transaction      : #1002 Wireless Mouse (270000.00)
  Total units sold        : 31
```

**c) Compare callbacks for sorting.** The hand-written sort takes a comparison
function pointer, so one sort routine serves four different orders (section 5).

### 4. Callback functions

A callback is a function **passed to another function and called by it**. The
program declares a callback type that receives the transaction and a context
pointer describing what to match:

```c
typedef int (*FilterFn)(const Transaction *, const void *);

int filter_above_amount(const Transaction *t, const void *context);  // context = double*
int filter_by_product  (const Transaction *t, const void *context);  // context = char*
int filter_min_quantity(const Transaction *t, const void *context);  // context = int*
```

`apply_filter()` walks the ledger and calls whichever callback it was given:

```c
int apply_filter(const Ledger *ledger, FilterFn matches, const void *context) {
  int i, found = 0;
  print_table_header();
  for (i = 0; i < ledger->count; i++)
    if (matches(&ledger->items[i], context)) {
      print_transaction(&ledger->items[i]);
      found++;
    }
  return found;
}
```

The three call sites each pass a different function and a different context:

```c
found = apply_filter(ledger, filter_above_amount, &amount);
found = apply_filter(ledger, filter_by_product, product);
found = apply_filter(ledger, filter_min_quantity, &minimum);
```

Filtering the captured ledger for totals of at least 500000 returns exactly the
two transactions above that line:

```

  1001  Laptop Pro 14                    2    850000.00     1700000.00  2026-11-20
  1004  Monitor 27in                     3    320000.00      960000.00  2026-11-23
```

### 5. Searching and sorting — written by hand

**Searching** is a plain loop with no library helper: by transaction ID (exact),
by product name (`strstr` on lowercased copies, so `mouse` finds `Wireless
Mouse`), and by exact total amount (compared with a small tolerance because the
values are floating point).

**Sorting** is a bubble sort implemented in the file. `qsort` is not used
anywhere. The comparison is a function pointer so the same loop handles all four
orders:

| Compare callback | Order |
|---|---|
| `compare_id_asc` | transaction ID |
| `compare_product_asc` | product name A-Z |
| `compare_total_asc` | total amount, smallest first |
| `compare_total_desc` | total amount, largest first |

```c
void sort_with(Ledger *ledger, CompareFn compare) {
  int i, j;
  for (i = 0; i < ledger->count - 1; i++)
    for (j = 0; j < ledger->count - 1 - i; j++)
      if (compare(&ledger->items[j], &ledger->items[j + 1]) > 0)
        swap_transactions(&ledger->items[j], &ledger->items[j + 1]);
}
```


The average is guarded: with no transactions the program says it is not
available instead of dividing by zero.

### 7. File handling

Transactions are saved to `sales_transactions.txt` as text:

```
5
1001|Laptop Pro 14|2|850000.00|2026-11-20
1002|Wireless Mouse|15|18000.00|2026-11-21
...
```

The first line is the count, and each following line holds one transaction with
`|` separators. On load the total is recomputed from quantity and price rather
than trusted from the file. A missing file is reported as "no saved file found",
and a malformed line is reported with its position instead of loading bad data.

The captured session proves persistence: save 5, load 5, delete one, save 4.

### 8. Input validation

| Input | Rule | On violation |
|---|---|---|
| menu choice | 1 to 12 | message and the menu returns |
| transaction ID | whole number, positive, unique | duplicate rejected |
| product name | not empty, fits the field | rejected |
| quantity | 1 to 10000 | rejected |
| unit price | greater than 0 | rejected |
| update / delete / search on a missing ID | must exist | "no transaction with ID" |
| average with no transactions | division by zero | "not available" |
| file open failure | checked on both save and load | specific error message |

Editing a transaction accepts an empty answer to keep the current value, so a
single field can be changed without retyping the record.
