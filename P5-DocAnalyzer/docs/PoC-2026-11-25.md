# P5 - Multi-threaded Document Search and Analysis System

## What the program does

The analyser takes a search keyword and any number of text files, gives **each
file its own thread**, and writes a separate report per file.

```
./docanalyzer "IoT" samples/document1.txt samples/document2.txt samples/document3.txt
```

Each thread searches its own file for the keyword, counts the occurrences and
the matching lines, records the line numbers, and writes a report next to the
input file, named after it (`document1.txt` becomes `document1_report.txt`).
The main thread creates the worker threads, joins every one of them, then
prints a summary.

### 1. Threading model

One `pthread_t` per input file, and one `ThreadArg` per file carrying everything
that thread needs:

```c
typedef struct {
  int thread_index;               // 1-based, used in every message
  char input_path[PATH_LEN];      // the file this thread analyses
  char output_path[PATH_LEN];     // where its report is written
  char keyword[KEYWORD_LEN];      // copy of the search keyword

  int total_lines;                // lines read from the input file
  int occurrences;                // keyword hits across the whole file
  int matching_lines;             // lines containing at least one hit
  int *line_numbers;              // numbers of the matching lines (heap)
  int line_capacity;

  int failed;                     // 1 when the file could not be processed
  int started;                    // 1 once its thread has actually been created
  char message[320];              // reason shown in the summary
} ThreadArg;
```

The keyword is copied into each argument block rather than pointing at `argv`,
so no thread depends on the lifetime of the argument vector, and there is no
shared mutable state at all — every thread touches only its own structure and
its own file. That is why no mutex is needed.

Main creates the threads, then joins every thread that was actually created:

```c
for (i = 0; i < file_count; i++) {
  if (pthread_create(&threads[i], NULL, process_file, &args[i]) != 0) { ... failed ... }
  args[i].started = 1;
}
for (i = 0; i < file_count; i++) {
  if (!args[i].started) continue;      // never join a thread that was not created
  pthread_join(threads[i], NULL);
}
```

The `started` flag matters: joining a `pthread_t` that was never created is
undefined behaviour, so a failed `pthread_create` is recorded and skipped.

### 2. What each thread does

`process_file()` is the thread entry point. For its own file it:

1. prints `[Thread N] Processing <file> ...` so the user can see it start,
2. opens the file and handles a missing or unreadable file,
3. reads it line by line with `fgets`,
4. lowercases each line and counts keyword hits with `strstr` in a loop, which is
   what makes the search **case-insensitive** (`IoT`, `iot` and `IOT` all match),
5. records the number of every line that contained at least one hit,
6. writes the report and prints `[Thread N] Successfully processed ...`.

Counting occurrences per line rather than per file means a line such as
"an IoT hub and an IoT gateway" contributes two occurrences but only one
matching line, and the report shows both numbers.

Line numbers are stored in a **dynamically grown array**:

```c
if (arg->matching_lines < arg->line_capacity) { ...store... }
new_capacity = arg->line_capacity * 2;
grown = realloc(arg->line_numbers, new_capacity * sizeof(int));
if (grown == NULL) { ...fail cleanly... }
```

so a file with thousands of matching lines is handled without a fixed limit.

### 3. Report generation

Each thread writes its own report, named by stripping the input extension and
adding `_report.txt` (`document1.txt` becomes `document1_report.txt`):

```
==============================================
  DOCUMENT ANALYSIS REPORT
==============================================
  Input file      : samples/document1.txt
  Search keyword  : IoT
  Total lines     : 12
  Occurrences     : 7
  Matching lines  : 6
  Status          : SUCCESS
  Line numbers    : 3, 5, 7, 8, 9, 11
==============================================
```

The "keyword not found" case is not an error — it reports zero occurrences and
says so explicitly:

```
  Occurrences     : 0
  Matching lines  : 0
  Status          : SUCCESS
  Line numbers    : none (the keyword does not appear in this file)
```

### 4. Thread status on the terminal

The main thread and the workers report on the terminal as work progresses:

```
  [Main] Creating thread 1 for samples/document1.txt
  [Thread 1] Processing samples/document1.txt ...
  [Main] 3 thread(s) started, waiting for them to finish...
  [Thread 1] Successfully processed samples/document1.txt (12 line(s), 7 occurrence(s))
```

Because the threads run concurrently, the order of those lines is not fixed —
that is the point of the exercise, and it is visible in
`outputs/sample_run.txt`.

### 5. Error handling

| Situation | Behaviour |
|---|---|
| too few arguments | prints the usage line with an example and exits with status 1 |
| the file cannot be opened | `[Thread N] ERROR: could not open <file>`, the file is marked FAILED in the summary |
| the file is empty | marked failed with "the file is empty" |
| a read error occurs (`ferror`) | marked failed with "error while reading <file>" |
| the report cannot be created or closed | marked failed and reported on the terminal |
| `pthread_create` fails | `[Main] ERROR: could not create thread N`, that file is skipped, and the remaining threads still run and are joined |
| out of memory while recording line numbers | the thread fails cleanly instead of writing past its buffer |

A failed file never stops the others: the summary lists each file as Completed
or FAILED with the reason.

### 6. Modular organisation

| Function | Job |
|---|---|
| `copy_lower` | lowercase a string into a buffer |
| `count_occurrences` | count non-overlapping keyword hits in a lowercased line |
| `remember_line` | append a matching line number, growing the array with `realloc` |
| `build_report_path` | turn `file.txt` into `file_report.txt` |
| `generate_report` | write one thread's report and report its own errors |
| `process_file` | the thread entry point: read, search, record, report |
| `print_summary` | per-file outcome, counts and the list of reports written |
| `main` | argument parsing, argument blocks, thread creation and joining |

### 7. Memory management

- `calloc` for the array of `ThreadArg` and for the array of `pthread_t`.
- `malloc` for each thread's line-number buffer, `realloc` as it fills.
- every allocation is checked before use.
- `main` frees every line-number buffer, then both arrays, once the threads have
  been joined.

Verified with AddressSanitizer and UndefinedBehaviorSanitizer on a three-file
run: exit status 0, no diagnostics, no leaks.
